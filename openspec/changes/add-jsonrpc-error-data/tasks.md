## 1. `Core::ErrorDetail<DATA>` — the single, explicit mechanism (Decision 1)

- [ ] 1.1 Add `Core::ErrorDetail<DATA>` (plain `Core::` namespace, not `Core::JSONRPC` — per CCB review) to `Source/core/` (e.g. `Source/core/Errors.h`), a minimal wrapper type with `Core::OptionalType<int32_t> Code` (a per-call override of `error.code`, the replacement for `CustomErrorCode`'s verbatim-code capability), `Core::OptionalType<string> Message` (the replacement for `CustomErrorCode`'s per-call text override), and `Core::OptionalType<DATA> Data` (also optional — per CCB review, so a method can set only `Code`/`Message` without a payload). `DATA` is templated and defined per adopting interface; `Code`/`Message` are fixed, non-templated fields shared by every instantiation
- [ ] 1.2 In `ThunderTools/JsonGenerator/source/header_loader.py`, recognize a parameter of type `Core::ErrorDetail<...>` **purely structurally**, by its C++ type name — mirroring the existing `Core::JSONRPC::Context` special-case — with **no** `@error`-style annotation tag (per CCB review); exclude it from `BuildResult`'s success-result schema entirely, and record it separately for `rpc_emitter.py`
- [ ] 1.3 In `ThunderTools/JsonGenerator/source/rpc_emitter.py`, emit an extra local `Core::OptionalType<Core::ErrorDetail<DATA>>` temporary for the recognized parameter, pass it by reference into the real interface call alongside the method's normal parameters, and — on the error path only, if it `IsSet()` — assign `Code` into `Error.Code` when present (overriding `SetError()`'s default-derived value for that call only), assign `Message` into `Error.Text` when present, and assign `Data` into `Error.Data` when present. Leave the handling of every other `@out`/response parameter on this method completely unchanged (never inspected or copied on the error path — Decision 2)
- [ ] 1.4 Confirm (via a `ProxyStubGenerator` test, not a change) that this parameter marshals with the same already-verified unconditional read/write behavior as any other `@out` parameter, in-process and out-of-process
- [ ] 1.5 Add an isolated sample/test interface (not `IAccount`/`IContentProtection` or any real production interface) exercising the full opt-in flow end to end for **two** method shapes: one that already declares other `@out` parameters, and one that declares none — both must require the identical `Core::ErrorDetail<DATA>` parameter, confirming Decision 2 (existing `@out` parameters grant no shortcut)
- [ ] 1.6 Within that sample interface's tests, cover: only `Data` set, only `Message` set (no `Data`), only `Code` set (no `Data`/`Message`), and all three set — asserting each wire field is present/overridden only when its corresponding member was set, and omitted/default otherwise

## 2. Verify existing `@out`/response parameters are never a source of `error.data` (Decision 2)

- [ ] 2.1 Add a regression test on a method that has an existing `@out`/response parameter, populates it, and returns an error **without** adopting `Core::ErrorDetail<DATA>` — confirm the wire response contains only `code`/`message`, with no `data` member and no trace of the populated parameter's contents (locks in today's existing discard behavior as a hard, permanent requirement, not an artifact still open to a future "free reuse" fix)
- [ ] 2.2 Add the same regression test for a method that **does** adopt `Core::ErrorDetail<DATA>` alongside other `@out` parameters — confirm those other `@out` parameters are still never copied into `error.data`, only the explicit `Core::ErrorDetail<DATA>` parameter's contents are

## 3. `error.data` wire representation (Decision 3 — open point, CCB comment 7)

- [ ] 3.1 Evaluate the two representations discussed in design.md Decision 3 for `Core::JSONRPC::Message::Info::Data` — (a) `Core::JSON::Variant`, or (b) generator-level serialization of the concrete `DATA` value directly into the response text — and pick one based on implementation complexity and consistency with the rest of `Info`'s `Core::JSON::Container` composition
- [ ] 3.2 Implement the chosen representation, ensuring: `data` is a real JSON value (object/array/scalar) on the wire, never a JSON-encoded string; `data` is omitted entirely from `ToString()` output when no adopted `Core::ErrorDetail<DATA>::Data` was set (matching today's behavior for the overwhelming majority of error responses)
- [ ] 3.3 Add unit tests asserting `Info.Data` round-trips each JSON-RPC-legal shape (`object`, `array`, `string`, `number`, `boolean`, `null`) through `ToString()`/`FromString()`, and that an unset `Info` still omits `data` from `ToString()` output

## 4. Remove legacy `CustomErrorCode` mechanism (Decision 4)

- [ ] 4.1 Confirm zero in-tree callers before removal: re-run a search for `Core::CustomCode`, `Core::IsCustomCode`, `Core::SetCustomCodeToStringHandler`, `CustomCodeToString`, `ICustomErrorCode` across `Thunder`, `entservices*`, and `ThunderTools` at the time of removal (baseline already found zero official-mechanism callers outside `Source/core` itself; `entservices-cpc/entservices-contentprotection`'s `IErrorToString` is a separate, self-built mechanism that does not call into this API and is unaffected)
- [ ] 4.2 Delete `Core::CustomCode()`, `Core::IsCustomCode()`, `CustomCodeToStringHandler`, and `SetCustomCodeToStringHandler` from [Source/core/Errors.h](../../../Source/core/Errors.h#L33-L46) / [Source/core/Errors.cpp](../../../Source/core/Errors.cpp)
- [ ] 4.3 Delete [Source/core/ICustomErrorCode.h](../../../Source/core/ICustomErrorCode.h) in full, and remove it from `Source/core/CMakeLists.txt`/`core.vcxproj` header lists
- [ ] 4.4 Delete the `CustomCodeLibrary` class and its associated config/wiring from [Source/Thunder/PluginHost.cpp](../../../Source/Thunder/PluginHost.cpp#L152-L206)
- [ ] 4.5 Remove the `IsCustomCode()` branch from `Info::SetError()` in [Source/core/JSONRPC.h](../../../Source/core/JSONRPC.h#L194) so every non-well-known `Core::hresult` falls through to the existing deterministic default (`ApplicationErrorCodeBase` offset) mapping unconditionally, unless overridden by an adopted `Core::ErrorDetail<DATA>::Code` (Task 1)
- [ ] 4.6 Remove the `IsCustomCode()`-checking branches inside `Core::ErrorToString()` and `Core::ErrorToStringExtended()` ([Source/core/Errors.cpp](../../../Source/core/Errors.cpp#L104-L129)) — after Task 4.2 these branches are dead code; the functions keep only their existing `_bogus_ErrorToString`/`"Undefined Thunder error code: <N>"` fallback path
- [ ] 4.7 Add a regression test (traced in design.md's worked example) asserting that an arbitrary, non-well-known `Core::hresult` (e.g. `21001`), on a method that has **not** adopted `Core::ErrorDetail<DATA>`, produces `error.code == ApplicationErrorCodeBase - 21001` and `error.message == "Undefined Thunder error code: 21001"` after removal
- [ ] 4.8 Replace [docs/utils/customcodes.md](../../../docs/utils/customcodes.md) with documentation for `Core::ErrorDetail<DATA>` (Task 1), including a short "if you used `CustomErrorCode` for per-call text/code, use this instead" migration note
- [ ] 4.9 Add a prominent breaking-change release note naming the removed public `EXTERNAL` symbols (`Core::CustomCode`, `Core::IsCustomCode`, `Core::SetCustomCodeToStringHandler`, `ICustomErrorCode.h`'s `CustomCodeToString` contract), since this was a documented, externally-loadable library contract whose out-of-tree usage cannot be ruled out by in-tree search alone

## 5. `JSONRPCErrorAssessor`: deprecation note only (Decision 5, CCB comment 5)

- [ ] 5.1 Make **no** functional or signature change to `JSONRPCErrorAssessor` ([Source/common/JSONRPC.h](../../../Source/common/JSONRPC.h#L1918-L1971)) as part of this proposal
- [ ] 5.2 Add a `@deprecated`-style documentation comment on the assessor type/registration API noting it is intended for future removal and should not be extended further; do not attach any new capability to it
- [ ] 5.3 File or reference a follow-up tracking item (outside this change) for an eventual removal/migration-away plan, since that is a separate proposal's scope

## 6. Documentation

- [ ] 6.1 Add/update JSON-RPC plugin-authoring documentation (e.g. under `docs/`) explaining: `Core::ErrorDetail<DATA>` is the **only** way to attach `error.data` or override `error.code`/`error.message`, applicable uniformly whether or not the method already has other `@out` parameters; existing `@out`/response parameters are never treated as an implicit source of error detail; `Code`/`Message` are fixed fields while `Data` is templated per adopting interface; all three are independently optional; the security note about not putting sensitive information in `Data`; and the ABI/interface-version cost of adopting it
- [ ] 6.2 Document, in the plugin-authoring notes, that out-of-process (COM-RPC-backed) plugins behave identically to in-process ones for this feature with no extra steps required by the plugin author (verified: COM-RPC already preserves output parameters, including the new `Core::ErrorDetail<DATA>` parameter, regardless of the returned error code)
- [ ] 6.3 Document the collision-risk guidance for interface owners who set `Code`: pick values outside Thunder's own reserved `ERROR_CODES` range and document the chosen range

## 7. Validation

- [ ] 7.1 Run the full existing JSON-RPC test suite in `Tests/` to confirm no regressions in error responses that don't adopt `Core::ErrorDetail<DATA>`
- [ ] 7.2 Add end-to-end coverage (client + server) exercising a real-shaped plugin method that adopts `Core::ErrorDetail<DATA>` and returns structured `data`/`code`/`message` overrides on error, confirming the serialized response matches the `jsonrpc-error-data` spec scenarios
- [ ] 7.3 Add end-to-end coverage for an **out-of-process** plugin method (COM-RPC-backed) that adopts `Core::ErrorDetail<DATA>` and returns an error, confirming parity with the in-process case
- [ ] 7.4 Add a regression test for a method with no opted-in `Core::ErrorDetail<DATA>` parameter (with or without other `@out` parameters) confirming its error response still contains only `code`/`message` with no `data` member and no override, after this change
