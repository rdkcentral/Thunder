## Why

Thunder's JSON-RPC error object (`Core::JSONRPC::Message::Info` in [Source/core/JSONRPC.h](../../../Source/core/JSONRPC.h#L64)) implements only `code` and `message` from the [JSON-RPC 2.0 error object spec](https://www.jsonrpc.org/specification#error_object). The optional `data` member — meant to carry structured, application-defined error detail — is declared as a plain `Core::JSON::String` and is never populated anywhere in the codebase. As a result, plugins have no spec-compliant way to return machine-readable error detail (validation failures, offending parameter names, nested COM-RPC error chains, etc.) alongside a JSON-RPC error.

In the absence of a real `data` channel, plugin authors and RDK integrators have improvised workarounds that the Thunder team wants to eliminate:
- Overloading `Error.Text` (the `message` field) with ad-hoc detail strings (`response->Error.Text = output` in [Source/Thunder/PluginServer.h](../../../Source/Thunder/PluginServer.h#L1112)), mixing human-readable summary and machine-readable detail in one untyped string.
- Returning `Core::ERROR_NONE` (a JSON-RPC success) with error detail smuggled into the `result` object instead, which violates the spec and breaks generic JSON-RPC client error handling.
- The existing `CustomErrorCode` mechanism ([Source/core/ICustomErrorCode.h](../../../Source/core/ICustomErrorCode.h), [Source/core/Errors.h](../../../Source/core/Errors.h#L33-L46)) only maps a single global, process-wide custom code to a replacement *string* for `message` — it cannot express structured `data`, cannot carry per-call context, and only supports one registered handler at a time ("can only set one, not multithreaded safe", per its own source comment).

RDK has requested first-class, spec-compliant error `data` support so plugins can surface structured diagnostic information to clients without abusing `message` or `result`. This has been discussed multiple times in the Thunder project (the partial `CustomErrorCode` feature was the last attempt); the team wants **one** coherent, call-specific mechanism as the single source of truth for custom error detail — including removing `CustomErrorCode` entirely — rather than maintaining it alongside a new, parallel feature. (Verification note: no in-tree caller of `Core::CustomCode()`/`Core::IsCustomCode()`/`Core::SetCustomCodeToStringHandler` was found in `Thunder`/`entservices*`/`ThunderTools`; the one closely related real-world need found in-tree, `entservices-cpc/entservices-contentprotection`'s `IErrorToString`, does not use this mechanism at all and independently reinvented its own per-plugin equivalent — see design.md for the full evidence trail.)

Thunder plugins are frequently out-of-process (OOP): a JSON-RPC request is dispatched to the plugin's real implementation over COM-RPC, with the JSON-RPC \<-\> C++ glue produced by the `JsonGenerator` tool and the COM-RPC proxy/stub marshaling produced by the `ProxyStubGenerator` tool (both in the sibling `ThunderTools` repository). Investigation confirmed the actual field-discarding behavior described above happens in `JsonGenerator`'s generated glue, not in COM-RPC itself — COM-RPC already delivers a plugin's populated output parameters across the process boundary intact regardless of the returned error code. This makes the fix a **cross-repository change** (`Thunder` + `ThunderTools`), not a `Thunder`-only one; see design.md for the verified evidence.

## What Changes

- Introduce a structured, spec-compliant `data` member on the JSON-RPC error object, populated from a value plugins can set when returning an error from a registered method/property handler.
- Provide a plugin-facing API to attach `data` (and optionally an overriding `message`) to the in-flight JSON-RPC error response, without changing the `uint32_t`/`Core::hresult` return-code contract that `Core::JSONRPC::Handler::Register` methods rely on today.
- Update `JsonGenerator` (`ThunderTools/JsonGenerator/source/rpc_emitter.py`) so the generated JSON-RPC method glue — which today only copies a plugin's populated response fields into the JSON response object when the method returns `Core::ERROR_NONE` — also does so on the error path, since COM-RPC already delivers those field values intact regardless of the returned error code (verified: no `ProxyStubGenerator`/COM-RPC change is required). This is the primary fix, covering the vast majority of real (in-process and out-of-process) plugin methods; a matching, smaller fix applies to the small set of hand-written `Register<INBOUND,OUTBOUND,METHOD,REALOBJECT>` call sites in `Source/core/JSONRPC.h` that bypass code generation.
- Preserve full backwards compatibility: existing responses that never set `data` must continue to omit the `data` member exactly as today (no `"data":""` regression), and `Error.Code` / `Error.Text` behavior from `SetError()` is unchanged. Existing generated plugin headers keep today's behavior until regenerated with the updated `JsonGenerator`, making rollout gradual and per-plugin.
- Provide an **explicit, opt-in** dedicated error-detail parameter mechanism (a reusable `Core::JSONRPC::ErrorDetail<DATA>` wrapper, recognized by `JsonGenerator`) that an interface owner may add to a method that has no reusable `@out` parameter (e.g. a void-response method) or that wants an error schema independent of its success-result schema. `ErrorDetail<DATA>` has two fixed fields — `Code` (`Core::OptionalType<int32_t>`) and `Message` (`Core::OptionalType<string>`) — plus a `Data` member whose type (`DATA`) is templated and defined per adopting interface. When a method sets `Code`/`Message` on this parameter before returning an error, that call's `error.code`/`error.message` are overridden verbatim, taking precedence over `SetError()`'s default-derived values for that call only; when left unset, `error.code`/`error.message` are derived exactly as they are for a method that hasn't opted in. This is not applied to any existing interface by this proposal — it is an ABI-affecting interface change an owner adopts deliberately, per method, separately from the zero-migration fix above.
- **Remove `CustomErrorCode` entirely** as the single source of truth for call-specific custom error detail: delete `Core::CustomCode()`/`Core::IsCustomCode()`/`CustomCodeToStringHandler`/`SetCustomCodeToStringHandler` from `Source/core/Errors.h`/`Errors.cpp`, delete `Source/core/ICustomErrorCode.h`, delete the `CustomCodeLibrary` dynamic-library-loading class from `Source/Thunder/PluginHost.cpp`, and simplify `Info::SetError()` to drop its custom-code branch. Its two legitimate capabilities — a call-specific replacement `message`, and an app-chosen value appearing verbatim as `error.code` — are replaced (not dropped) by the opt-in `ErrorDetail<DATA>`'s `Message`/`Code` fields above, now scoped per-method/per-call rather than a global, process-wide handler. This is an intentional, documented breaking change to public `EXTERNAL` Core symbols; see design.md Decision 5 for the full risk/mitigation analysis.

## Capabilities

### New Capabilities
- `jsonrpc-error-data`: Structured `data` field support on the JSON-RPC 2.0 error object — the wire format, the plugin-facing API for setting it, propagation through synchronous/async/error-assessor invoke paths, and backwards-compatibility guarantees (omit when unset).

### Modified Capabilities
- (none — `CustomErrorCode` and the JSON-RPC dispatch path are existing implementation, not previously specified capabilities; this proposal specifies `jsonrpc-error-data` as the first formal spec covering this area. `CustomErrorCode`'s removal is documented as an implementation change in design.md/tasks.md rather than an openspec capability delta, since it was never itself a previously-specified capability.)

## Impact

- **Affected code**:
  - `Source/core/JSONRPC.h` — `Message::Info` (error object model), `Message::Info::SetError()`, `InternalRegisterImplIO`/`InternalRegisterImpl<OUTBOUND,...>` (hand-written `Register<>` path only).
  - `Source/common/JSONRPC.h` — `PluginHost::JSONRPC::InvokeHandler`/`InvokeOnHandler`, `JSONRPCErrorAssessor` callback signature.
  - `Source/Thunder/PluginServer.h` — synchronous dispatch error-response assembly (~line 1110), parse-failure paths (~lines 4776, 4924, 5358).
  - `Source/websocket/JSONRPCLink.h` — client-side async/timeout/abort error assembly (~lines 395–414).
  - `Source/core/Errors.h` / `Errors.cpp`, `Source/core/ICustomErrorCode.h` — **deleted**: `Core::CustomCode()`, `Core::IsCustomCode()`, `CustomCodeToStringHandler`/`SetCustomCodeToStringHandler`, and `ICustomErrorCode.h` in full (Decision 5).
  - `Source/Thunder/PluginHost.cpp` — **deleted**: the `CustomCodeLibrary` dynamic-library-loading class and its associated config wiring (~lines 152–206).
  - `docs/utils/customcodes.md` — replaced with documentation for the new opt-in `ErrorDetail<DATA>`/`Message` mechanism, including a migration note for the removed API.
  - **`ThunderTools/JsonGenerator/source/rpc_emitter.py`** (sibling repository) — the primary fix: generated JSON-RPC glue must stop discarding populated response fields on the error path. Every plugin's generated `J*.h` header must be regenerated to gain the capability. Also gains recognition of the new, opt-in `Core::JSONRPC::ErrorDetail<DATA>` parameter shape (`header_loader.py`/`rpc_emitter.py`), for interfaces that choose to adopt it.
  - `ThunderTools/ProxyStubGenerator/` — inspected, **no change required** (COM-RPC stub/proxy code already marshals output parameters unconditionally, regardless of the returned `hresult`), including for the new opt-in parameter shape, which marshals like any other `@out` parameter.
- **API impact**: New public API surface for setting error `data` from a method handler (additive, non-breaking); potential signature change to the `JSONRPCErrorAssessor` callback type (documented as a breaking change if unavoidable, otherwise an additive overload). A method that opts into `ErrorDetail<DATA>` and sets its `Code`/`Message` fields changes that call's `error.code`/`error.message` from the framework's default-derived values to the plugin's own — additive/opt-in per method, not a change to any existing method's observed behavior unless its owner adopts it. **Additionally, an intentional breaking change**: removal of the public `EXTERNAL` Core symbols `Core::CustomCode`, `Core::IsCustomCode`, `Core::SetCustomCodeToStringHandler`, and the `ICustomErrorCode.h` externally-loadable library contract (Decision 5) — call out explicitly and prominently in release notes, since this contract is designed to be implementable outside this workspace and cannot be proven unused purely by in-tree search.
- **Wire format impact**: JSON-RPC error responses may now include a `data` member where previously they did not — additive per spec, but downstream consumers doing strict schema validation on error objects should be noted in release notes.
- **Dependencies**: No new external dependencies within `Thunder` itself. Interacts with existing `Core::JSON::Variant`/`Core::JSON::Container` JSON framework in `Source/core/JSON.h`. Introduces a **cross-repository dependency on `ThunderTools`**: this change cannot be considered complete for generated (the vast majority of) plugins until the `JsonGenerator` fix ships and affected plugins regenerate their JSON-RPC glue.
